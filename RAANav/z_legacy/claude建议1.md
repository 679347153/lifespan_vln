## 二、当前实现是什么性质

**是的，当前是基于仿真"上帝视角"（Ground Truth）提取的。** 具体来说：

- `scene_extract.py` 直接读取 Habitat 的 `semantic_scene` 语义场景图，这是 HM3D 标注好的 GT 数据
- 物体的 category、AABB、OBB、room 归属全部来自标注，不涉及任何**感知**过程（没有用视觉模型去检测/分割）
- 栅格地图通过 navmesh 随机采样生成，也是利用了仿真的 GT 导航网格

**这作为第一版是正确的做法** —— 先验证下游模块（融合、评分、GMM输出）在理想输入下能不能跑通，再逐步替换为感知输入。

| 问题 | 严重度 | 说明 |
|------|--------|------|
| `clip_embedding` 为空 | **高** | 所有物体的 CLIP 向量为 `[]`，CLIP_RAG 查询、R_sim 计算全部无法工作 |

| R_objs 过于密集 | **中** | 平均每物体 4 个关系，但因 AABB 偏大导致部分关系是假阳性 |
| 无视觉感知管线 | **高** | 当前完全依赖 GT，没有从 RGB-D 帧检测/分割物体的能力 |
| 栅格地图未连通优化 | **低** | navigable_mask 有些碎片化，可进一步形态学处理 |

### 3.2 架构层面的 Gap

从**当前状态**到**仿真闭环**（Step 5），缺失的核心模块：

```
当前：GT物体提取 → 静态Map JSON → 静态GMM查询
          ↓ 需要补充的
目标：Agent行走 → 逐帧RGB-D → 在线感知 → 增量建图 → 查询 → 导航决策 → 循环
```

缺失的关键组件：
1. **在线物体检测/分割** — 从 RGB 帧中识别物体（可用 GroundedSAM/YOLO-World/开放词汇检测器）
2. **深度反投影 → 物体3D定位** — 从 2D 检测 + 深度图反推世界坐标（`occupancy_grid.py` 的 `_depth_to_pointcloud` 已实现基础版）
3. **导航策略/Planner** — 根据 GMM Top-K 候选点规划路径（需接入 Habitat 的 pathfinder）
4. **探索闭环控制器** — 决定何时停止、何时换目标点、何时声明失败

## 四、对你计划的建议

读完你所有规划文档后，有几点值得讨论：

### 建议 1：补齐 CLIP embedding 应该是下一优先级

现在 264 个物体的 `clip_embedding` 全为空，导致整个 RAG 评分通道 ($R_{sim}$) 瘫痪。你已有 `CLIP_RAG/runtime_clip_index.py`，只需：
- 对 GT 物体：用 label 文本编码 CLIP 向量（纯文本方式，几秒完成）
- 对感知物体：用裁剪图像编码 CLIP 向量（后续替换）

**建议在 `map_Create.py` 的 Step 2 之后加一步自动填充 CLIP embedding。**

### 建议 2：不要跳过"半仿真"阶段直接做在线感知

你的规划中提到从 GT 直接跳到完整感知闭环。我建议加一个**中间阶段**：

```
GT建图 → [半仿真] → 完整感知闭环
```

**半仿真**意思是：机器人在 Habitat 里行走，用仿真的 GT 语义分割（semantic sensor 已有每帧输出）代替视觉检测模型，但执行的是**在线增量建图**流程。这样可以：
- 验证增量地图融合（`map_Update`）在多帧连续输入下是否正常
- 验证 GMM → 导航点 → pathfinder 的闭环
- 不被 YOLO/SAM 的检测精度干扰，先隔离验证导航逻辑

### 建议 3：你的 $R_{cfd}$ 关联置信计算需要修正

规范中 $R_{cfd}$ 依赖 `cooccur_stats`，但当前 GT 提取只执行了一次（N=1），所有共现次数都是 1，无法体现统计意义。**建议**：
- 多轮扫描（T1/T2/T3）后才有有意义的共现统计
- 或在 GT 建图时，用空间邻近关系 + 类别先验预设初始共现值

### 建议 4：关于 Sim2Real 的轻量化考虑

你提到要部署到真实小车，这对以下几个组件有约束：

| 组件 | 仿真中 | 真实部署约束 |
|------|--------|-------------|
| 物体检测 | GT semantic | 需轻量模型（YOLO-World-S、MobileSAM） |
| CLIP 编码 | ViT-B/32 | ✅ 已经足够轻量 (~150MB) |
| LLM Agent | Qwen-Plus API | 网络延迟！建议离线时用、导航时缓存 |
| 栅格地图 | navmesh采样 | 需改成在线深度投影（已实现框架） |
| GMM 计算 | numpy | ✅ 够轻量 |

**最大瓶颈是 LLM API 延迟。** 建议：
- Agent 只在**任务开始**和**验证失败**时调用（不是每步都调用）
- 预先缓存常见查询的 room-level 先验（你的 $P_{agent}(room|q)$）
- 考虑本地小模型替代（Qwen-1.8B / Phi-3-mini）

### 建议 5：你规划中的一个不合理处

可执行技术规范 §3.2 的时间衰减半衰期建议是 3 天，但你的仿真实验中 T1/T2 的时间差是人为设定的。如果用真实 `datetime` 存储但帧间间隔只有几秒，$\exp(-\lambda \Delta T)$ 几乎恒为 1.0，**时间衰减完全失效**。

**建议**：在仿真实验中使用可配置的"虚拟时钟"——例如每帧前进 1 小时或每次完整扫描视为 1 天。否则论文中时间衰减的消融实验无法展示效果。
