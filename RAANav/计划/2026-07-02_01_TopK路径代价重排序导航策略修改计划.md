# 01 Top-K 路径代价重排序导航策略修改计划

日期：2026-07-02  
修订日期：2026-07-06

## 2. 是否立即实施 Top-K 路径重排序

原触发条件：

```text
ghr5_rate >= 0.45
found_rate <= 0.25
ghr5_to_found_gap / subtasks >= 0.20
```

当前实际：

```text
ghr5_rate = 0.175676
found_rate = 0.148649
ghr5_to_found_gap / subtasks = 0.027027
```

结论：

```text
当前不应立即把 Top-K 路径代价重排序作为第一优先级。
```

原因是：Top-K 候选本身离目标还不够近。若此时直接做路径代价重排序，可能只是从一批质量不高的候选中选择更近、更可达的错误候选，无法根本提升成功率。

本计划调整为：

```text
阶段 A：候选质量与目标确认修复
阶段 B：重新诊断 GHR@5 / Found 掉点
阶段 C：若触发条件满足，再实施 Top-K 路径代价重排序
```

### 3.3 增强候选排序诊断

当前 `candidate_recall_rate = 1.0` 但 `ghr5_rate = 0.175676`，说明候选列表存在，但 Top-K 质量低。需要新增或重点查看：

```text

top-1 / top-3 / top-5 / top-10 的命中率
selected candidate 的 label 是否命中 target alias

label_fallback、text_fallback 与 remote_clip 的命中差异
```

若发现 `text_fallback` 经常选到错误但语义相近的对象，应降低其权重或要求更严格的 alias/CLIP 一致性。

### 3.4 检查记忆迁移过多问题

当前：

```text

migrated = 4707
```

迁移比例偏高，可能表示：

- 同类物体被过度合并为一个 track。
- CLIP migration threshold 偏松。
- pseudo-room 内大量相似物体被合并。
- label 清洗后不同实例共享同一 canonical label，导致空间迁移过多。

建议检查：

```text
按 label 统计 migrated 事件
按 room 统计 migrated 事件
高迁移 object track 的位置历史
迁移前后距离分布
```

第一版可先不修改 memory 结构，只通过诊断确认是否需要收紧：

```text
merge_distance
migration_distance
clip_migration_threshold
```

## 4. 阶段 A：修复目标确认与 3D 定位

当前：

```text
perception_found = 32
found = 11
perception_found_rate - found_rate = 0.283783
```

这说明模型“认为看到目标”的次数远高于 benchmark success。需要优先排查：

### 4.1 spatial confirmation 是否过严或坐标偏移

当前使用：

```bash
--target-confirmation-mode spatial
--target-confirmation-margin 1.0
```

不建议立刻放宽 margin，因为会虚高成功率。应先输出诊断：

```text
perception_found detection position
GT target position
detection_to_gt_distance
depth source: mask median / bbox center
camera pose
```

若大量 perception_found 的检测点距离 GT 仅略大于 1.0m，可以再考虑：

```text
target_confirmation_margin = 1.25 或 1.5
```

但正式结果应同时报告 margin 消融。

### 4.2 检查 false positive confirmation

对于 `perception_goal_mismatch_or_false_positive_confirmation = 24` 的样例，应逐个查看：

```text
检测 label 是否真的命中 alias
检测 crop 是否是目标对象
是否同类不同实例
是否因为 label 过泛导致误确认
```

例如 `vase`、`stool`、`bottle`、`clock` 这类对象在室内可能有多个实例，spatial 模式必须避免“看到同类物体就成功”。

## 6. 阶段 C：Top-K 路径代价重排序方案

当阶段 B 满足触发条件后，再实施本节。

当前导航选点近似为：

```text
selected = argmax S_final(object)
```

计划改为：

```text
S_nav =
  S_final
  - alpha * normalized_geodesic_distance
  - beta  * revisit_penalty
  + gamma * visibility_gain
  + eta   * room_score
```

其中：

- `S_final`：已有 RAG / Agent 融合候选分数。
- `normalized_geodesic_distance`：当前 agent 到候选点的归一化 Habitat geodesic 距离。
- `revisit_penalty`：重复访问 object / room 和 negative feedback 的惩罚项。
- `visibility_gain`：候选点附近可见区域或探索收益。
- `room_score`：候选 object 当前 room belief。

候选选择改为：

```text
selected = argmax S_nav(candidate)
```

- 若 Top-K 为空，则保留现有 fallback。
- 若 nav rerank 计算失败，则降级到原 `S_final` Top-1。

## 11. 风险与假设

假设：

- 当前 74-subtask 结果来自真实 Habitat temporal loop。
- 远程感知链路已正常运行，`failures = 0`。
- 现在的主要问题不是无候选，而是候选质量、目标确认和部分导航转换。

风险：

- 如果 perception 误检仍然严重，nav rerank 只能更高效地导航到错误候选。
- 如果 target map alias 过泛，GHR@5 可能被大量同类干扰拉低。
- 如果 spatial confirmation 的 3D 坐标偏差未修，Found 仍可能低于 perception_found。
- 如果 visibility gain 权重过高，可能偏向开放区域而非目标高概率区域。
- pseudo-room 不是语义房间，room_score 只能作为弱先验。

## 12. 当前优先级结论

根据 2026-07-06 复测结果，当前阶段优先级修订为：

```text
P0: 保留 label sanitizer，但收紧 target alias，避免泛化 alias 直接参与强匹配和成功确认
P1: 将 alias 分为 strong_alias / weak_alias
P2: query_label_matches、perception_found、候选高分匹配只使用 strong_alias
P3: weak_alias 仅用于 prompt 扩展和 remote CLIP 文本检索，不用于 spatial confirmation
P4: 重新跑 74 subtasks，对比 found、GHR@5、GHR@10、avg_top1_dist、avg_top10_min_dist
P5: 若 GHR@5/GHR@10 上升但 Found 仍低，再实施 Top-K 路径代价重排序
```

一句话结论：

```text
最新复测显示 label 清洗本身有效，但 target alias 扩展过宽导致成功率下降；下一步应先做强/弱 alias 分级和确认规则收紧，再考虑 Top-K 路径重排序。
```
