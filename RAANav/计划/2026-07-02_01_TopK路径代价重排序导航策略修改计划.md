# 01 Top-K 路径代价重排序导航策略修改计划

日期：2026-07-02

本文记录“Top-1 Object 选点升级为 Top-K + 路径代价重排序”的完整修改方案。本文件仅作为后续实施计划记录，暂不实施代码改动。

## 1. 修改背景与有效性分析

当前真实 Habitat 闭环中的导航选点策略近似为：

```text
selected = argmax S_final(object)
```

也就是说，系统在候选物体经过 RAG / Agent 融合评分后，直接选择 `S_final` 最高的 object 位置作为下一轮导航目标点。

该策略简单直接，但存在明显局限：

- 容易选择语义分数最高但路径很远的候选点。
- 容易重复访问已经失败过的 object 或 pseudo-room。
- 没有显式考虑候选点附近的可见区域或探索增益。
- 没有利用当前已经构建的 room-level belief。
- 当远程 CLIP 或 label 匹配分数偏高时，导航会被单个错误候选牵引。

因此，从 Top-1 Object 选点升级为 Top-K + 路径代价重排序是有效且可行的。

该方案与 ObjectNav 中常见做法一致：目标选择不应只依赖语义分数，还应综合导航代价、探索收益和历史反馈。SemExp 将语义地图与 long-term goal policy 结合，PONI 将“去哪找目标”建模为 potential function，再交给 navigation skill 执行。当前项目也可以用最小侵入方式引入类似思想。

结论：

- 该方案有效且可行。
- 属于最小侵入式导航策略升级。
- 不改 perception 和 memory 主结构。
- 第一版只改 `run_temporal_habitat_loop` 的真实 Habitat 闭环。
- `visibility_gain` 使用真实 Habitat depth 环视估计，但必须可开关以控制运行成本。

## 2. 总体方案

当前流程：

```text
SceneMemory
  -> rank_candidates / remote CLIP rerank
  -> candidates[0]
  -> Habitat navmesh step_to()
```

计划改为：

```text
SceneMemory
  -> rank_candidates / remote CLIP rerank
  -> Top-K candidates
  -> 对 Top-K 计算导航代价、重复访问惩罚、可见增益、房间置信度
  -> 计算 S_nav
  -> selected = argmax S_nav
  -> Habitat navmesh step_to()
```

核心原则：

- 仍保留 `S_final` 作为语义 / RAG / Agent 主分数。
- 只在 Top-K 内做导航重排序，避免扩大计算开销。
- 不改变远程感知 API。
- 不改变 SceneMemory 主结构。
- 不改变 benchmark episode schema。
- 新策略必须可通过 `--no-nav-rerank` 关闭，以便与原始 Top-1 策略做消融。

## 3. 导航重排序公式

新策略为：

```text
S_nav =
  S_final
  - alpha * normalized_geodesic_distance
  - beta  * revisit_penalty
  + gamma * visibility_gain
  + eta   * room_score
```

其中：

- `S_final`：当前已有的 RAG / Agent 融合候选分数。
- `normalized_geodesic_distance`：当前 agent 到候选点的归一化 Habitat geodesic 距离。
- `revisit_penalty`：重复访问 object / room 和 negative feedback 的惩罚项。
- `visibility_gain`：候选点附近可见区域或探索收益。
- `room_score`：候选 object 当前 room belief。

候选选择改为：

```text
selected = argmax S_nav(candidate)
```

### 3.1 路径代价

对 Top-K 候选分别构造 candidate pose，并先 snap 到 navmesh：

```text
candidate_pose = snap_pose(candidate.world_x, current_y, candidate.world_z)
```

然后计算：

```text
geodesic_distance = adapter.geodesic_distance(current_pose, candidate_pose)
```

在当前 Top-K 内归一化：

```text
normalized_geodesic_distance = geodesic_distance / max_geodesic_distance
```

若候选不可达，距离为 `inf` 或无效，则该候选降到最低优先级；若所有候选都不可达，则走原 fallback。

### 3.2 重复访问惩罚

每个 subtask 内维护：

```text
visited_obj_counts
visited_room_counts
```

重复访问惩罚：

```text
obj_penalty  = 1 - exp(-visited_obj_count)
room_penalty = 1 - exp(-visited_room_count)
neg_penalty  = 1 - exp(-negative_feedback_count)

revisit_penalty =
  0.4 * obj_penalty
  + 0.3 * room_penalty
  + 0.3 * neg_penalty
```

每次选中候选后，更新对应 object 与 room 的访问计数。

### 3.3 可见增益

第一版使用真实 Habitat depth 环视估计 `visibility_gain`。

方法：

1. 对每个候选 pose 临时调用 Habitat `observe()`。
2. 不调用远程 perception，只使用本地 depth。
3. 使用 `visibility_views` 个方向做环视。
4. 从 depth 图中按 `visibility_depth_stride` 采样有效深度点。
5. 将可见点投影到地面网格。
6. 统计唯一可见 grid cell 数。
7. 在当前 Top-K 内归一化为 `[0, 1]`。

缓存键建议：

```text
(round(x, 2), round(z, 2), visibility_views, visibility_depth_stride)
```

这样可避免同一候选在同一 episode / subtask 内重复渲染。

注意：

- 该方案比轻量近似更准确。
- 但会增加本地 Habitat 渲染开销。
- 必须通过参数控制 Top-K、视角数和 depth stride。

### 3.4 Room Score

第一版不推断“目标真实房间”，避免引入错误先验。

使用候选 object 当前房间置信度：

```text
room_score = room_belief[current_room_id]
```

若 object 没有 `room_belief` 或 `current_room_id`，则：

```text
room_score = 0.0
```

## 4. 参数与默认值

新增命令行参数建议：

```bash
--nav-rerank / --no-nav-rerank
--nav-rerank-top-k 10
--nav-alpha 0.25
--nav-beta 0.20
--nav-gamma 0.20
--nav-eta 0.10
--visibility-views 4
--visibility-depth-stride 24
--visibility-grid-size 0.5
--visibility-max-depth 5.0
```

默认参数：

```text
alpha = 0.25
beta  = 0.20
gamma = 0.20
eta   = 0.10
nav_rerank_top_k = 10
visibility_views = 4
visibility_depth_stride = 24
visibility_grid_size = 0.5
visibility_max_depth = 5.0
```

默认行为：

- `--nav-rerank` 默认开启。
- `--no-nav-rerank` 用于保留原 Top-1 Object 策略作为消融。
- 若 Top-K 为空，则保留原 fallback 逻辑。
- 若导航重排序失败，应降级为原 `S_final` Top-1，而不是中断实验。

## 5. 实现位置

建议只改真实 Habitat 闭环相关逻辑：

```text
RAANav/AgenticRAG/benchmark_adapter/run_temporal_habitat_loop.py
RAANav/AgenticRAG/benchmark_adapter/visualize_temporal_run.py
```

### 5.1 run_temporal_habitat_loop.py

主要改动：

- 在 `_rank_with_remote_clip()` 返回候选之后、选择 `candidates[0]` 之前新增 nav rerank。
- 新增函数：

```text
rerank_candidates_for_navigation(...)
estimate_visibility_gain(...)
candidate_room_score(...)
candidate_revisit_penalty(...)
```

推荐数据流：

```text
candidates = _rank_with_remote_clip(...)

if args.nav_rerank and candidates:
    candidates = rerank_candidates_for_navigation(
        candidates,
        current_pose=loop.current_pose or current_pose,
        loop=loop,
        args=args,
        visited_obj_counts=visited_obj_counts,
        visited_room_counts=visited_room_counts,
    )

selected = candidates[0]
target_pose = _pose_from_candidate(selected, loop.current_pose or current_pose)
```

### 5.2 visualize_temporal_run.py

主要改动：

- Candidate 表格增加：

```text
S_nav
geo_cost
visibility_gain
revisit_penalty
room_score
selected_by
```

- 2D / 3D 可视化中高亮 nav rerank 选中的候选。
- 保留原始 `S_final` 排名，便于对比“语义 Top-1”和“导航 Top-1”是否不同。

当关闭 nav rerank 时：

```json
{
  "selected_by": "S_final_top1"
```

可视化应支持：

- 查看每轮原始 `S_final` 排名。
- 查看每轮 `S_nav` 排名。
- 查看最终被选中的候选。
- 查看导航重排序各项分解值。
- 判断是否因为路径远、重复访问、visibility 低而改变选择。

## 7. 测试计划

### 7.1 静态检查

```bash
python -m py_compile \
  RAANav/AgenticRAG/benchmark_adapter/run_temporal_habitat_loop.py \
  RAANav/AgenticRAG/benchmark_adapter/visualize_temporal_run.py
```

### 7.2 单元测试场景

构造 3 个候选：

- A：高 `S_final`，但路径远。
- B：中等 `S_final`，路径近。
- C：中等 `S_final`，visibility 高。

验证：

- `S_nav` 排序符合公式。
- geodesic distance 为 `inf` 时不应被选为 Top-1，除非所有候选都不可达。
- 同一 object / room 被重复访问后，`revisit_penalty` 上升并改变排序。
- 无 `room_belief`、无 negative feedback、无 visibility cache 时不报错。
- `--no-nav-rerank` 时结果退回原始 `S_final` Top-1。

## 8. 假设与风险

### 8.1 假设

- 第一版只改 `run_temporal_habitat_loop` 的真实 Habitat 闭环。
- 不改 offline eval 和 legacy smoke 脚本。
- `visibility_gain` 使用真实 Habitat depth 环视估计，不调用远程 GroundingDINO / MobileSAM。
- `room_score` 先使用候选自身 `current_room_id` 的 belief，不做目标房间预测。
- 若性能过慢，优先降低 `--nav-rerank-top-k`、`--visibility-views`，或增大 `--visibility-depth-stride`。

### 8.2 风险

- 真实 depth 环视会增加 Habitat 渲染开销。
- 若 geodesic distance 计算频繁，Top-K 太大时会拖慢每个 round。
- visibility gain 如果权重过高，可能偏向开放区域而不是目标高概率区域。
- room_score 当前基于 pseudo-room，不等同于真实语义房间。
- 如果 perception 本身召回很差，nav rerank 只能改善候选选择，不能解决候选为空的问题。

### 8.3 后续增强方向

- 将 `room_score` 从候选自身 room belief 升级为目标 room prior。
- 将 visibility gain 从 depth cell 数升级为 semantic frontier / unseen area gain。
- 将 `S_nav` 进一步扩展为 GMM / potential field 形式。
- 在可视化中画出候选重排序前后排名变化曲线。
