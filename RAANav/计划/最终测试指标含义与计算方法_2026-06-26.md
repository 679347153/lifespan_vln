# 最终测试指标含义与计算方法

本文档说明当前 RAANav / Agentic-RAG 长期家庭环境评测中各类指标的含义、来源文件和计算方式。适用对象主要是以下入口产生的结果：

```bash
python -m RAANav.AgenticRAG.benchmark_adapter.run_temporal_habitat_loop ...
```

该入口会在 `--output-dir` 下生成轨迹、候选、观测、记忆更新、负反馈、布局切换和 benchmark 汇总文件。最终指标不是单一分数，而是由三层结果共同构成：

- Benchmark 指标：衡量 agent 是否真正到达目标，以及路径效率。
- 记忆与检索指标：衡量长期记忆是否能给出接近目标的候选。
- 感知与调试指标：衡量远程 GroundingDINO / MobileSAM / CLIP 感知、候选生成和失败原因。

## 一、主要输出文件

一次完整运行通常会生成以下文件：

| 文件 | 作用 |
| --- | --- |
| `run.jsonl` | 每个 episode 的完整轨迹，包含子任务轨迹、路径长度、最终位姿和记忆统计。 |
| `episode_results.jsonl` | benchmark evaluator 对每个 episode 的评测结果。 |
| `summary.json` | episode 级总体指标，如 `success_rate`、`spl`、`avg_steps`。 |
| `by_task_type.json` | 按任务类型分组的子任务指标，如 `open_vocab`、`image_goal`、`language_goal`。 |
| `exploration_curve.json` | 按 `seen_layout_count_before` 分组的长期曲线。 |
| `memory_diagnostics.jsonl` | 每个 subtask 的检索、候选、目标距离和成功状态诊断。 |
| `temporal_summary.json` | 按时间状态和历史 layout 数聚合的长期记忆诊断。 |
| `candidate_traces.jsonl` | 每轮候选生成、候选分数、候选来源和 fallback 原因。 |
| `observation_traces.jsonl` | 每步感知到的目标标签、位置、CLIP embedding 维度等观测信息。 |
| `memory_updates.jsonl` | scene-level memory 的新增、合并、迁移和更新事件。 |
| `negative_feedback.jsonl` | 搜索失败后对旧候选位置施加负反馈的记录。 |
| `layout_transitions.jsonl` | 同一 scene 内 layout 进入、退出和 memory snapshot 路径。 |
| `scene_memory/*/scene_memory_final.json` | 每个 scene 最终持久化的长期记忆。 |
| `memory_snapshots/` | 每个 episode 或 layout 之后的记忆快照。 |
| `perception_summary.json` | 远程感知调用次数、耗时、失败数等统计。 |
| `adapter_warnings.json` | episode / layout 适配阶段的警告。 |
| `target_name_normalization.json` | 本次运行使用的目标名称归一化和别名映射。 |
| `visual_debug/index.html` | 可视化调试页面，用于查看轨迹、候选、目标和记忆事件。 |

## 二、Benchmark 总体指标

这些指标主要来自 `summary.json`，由 `benchmark/evaluate.py` 和 `benchmark/metrics.py` 计算。

### 1. `episodes`

含义：参与聚合统计的 episode 数量。

计算：

```text
episodes = len(evaluated_episode_results)
```

注意：这里是成功被 evaluator 匹配并评测的 episode 数，不一定等于原始数据集中 episode 总数。

### 2. `evaluated_episodes`

含义：成功完成评测的 episode 数。

计算：

```text
evaluated_episodes = len(results)
```

它与 `episodes` 通常相同。若有轨迹找不到对应 episode，相关条目不会进入评测。

### 3. `trajectory_count`

含义：`run.jsonl` 中读取到的轨迹数量。

计算：

```text
trajectory_count = len(trajectories)
```

如果 `trajectory_count > evaluated_episodes`，说明有轨迹没有匹配到 episode 定义。

### 4. `missing_episode_count`

含义：轨迹存在，但 evaluator 找不到对应 episode JSON 的数量。

计算：

```text
missing_episode_count = len(missing_episode_ids)
```

理想情况下应为 `0`。如果大于 `0`，说明 `--episodes`、`--split-manifest` 或输出目录中的 episode id 对不上。

### 5. `success_rate`

含义：episode 级成功率。一个 episode 只有在其中所有 subtask 都成功时，才算成功。

子任务成功条件：

```text
distance_to_goal <= success_radius
```

episode 成功条件：

```text
episode_success = all(subtask.success) and
                  len(subtask_results) == len(episode.subtasks)
```

总体成功率：

```text
success_rate = successful_episodes / evaluated_episodes
```

解读：

- 这是最严格的最终指标。
- 如果一个 episode 有多个目标，只要任一 subtask 失败，该 episode 的 `success` 就是 `false`。
- 因此 `success_rate = 0.0` 不代表所有子任务都完全失败，需结合 `by_task_type.json` 和 `memory_diagnostics.jsonl` 查看。

### 6. `spl`

含义：Success weighted by Path Length，成功加权路径效率。它同时考虑是否成功和路径是否接近最短路径。

单个 episode 的计算：

```text
if not success or shortest_path_length <= 0:
    SPL = 0
else:
    SPL = shortest_path_length / max(path_length, shortest_path_length)
```

总体 SPL：

```text
spl = mean(SPL_i for each episode i)
```

解读：

- 如果 episode 未成功，则该 episode 的 SPL 必为 `0`。
- 如果成功且实际路径等于最短路径，则 SPL 接近 `1`。
- 如果成功但绕路严重，则 SPL 位于 `0` 到 `1` 之间。
- 当前实验中若 `success_rate = 0.0`，则 `spl` 必然也是 `0.0`。

### 7. `avg_steps`

含义：平均每个 episode 执行的步数。

计算：

```text
avg_steps = mean(episode.steps)
```

在 `run_temporal_habitat_loop` 中，episode 的 step 来自所有 subtask trace 的 `steps` 之和；单个 subtask 的步数受以下参数影响：

- `--max-steps-per-subtask`
- `--max-rounds`
- `--micro-steps-per-round`
- 是否提前到达或被截断

解读：

- `avg_steps` 越高通常表示搜索更充分，但也可能意味着目标难找或策略低效。
- 如果经常接近 `--max-steps-per-subtask` 上限，说明搜索经常耗尽预算。

### 8. `avg_elapsed_seconds`

含义：平均每个 episode 的运行耗时，单位为秒。

计算：

```text
avg_elapsed_seconds = mean(trajectory.elapsed_seconds)
```

解读：

- 该指标受远程感知服务、SSH tunnel、Habitat 渲染、GPU 负载影响。
- 它不是算法路径效率指标，而是系统吞吐和工程性能指标。

### 9. `avg_path_length`

含义：平均每个 episode 实际行走路径长度，单位通常为米。

计算：

```text
avg_path_length = mean(episode.path_length)
```

episode path length 来自所有 subtask trace 的路径长度求和：

```text
episode.path_length = sum(trace.path_length for trace in subtask_traces)
```

解读：

- 与 `avg_shortest_path_length` 对比可看出绕路程度。
- 仅路径短不代表成功，必须结合 `success_rate` 与 `distance_to_goal`。

### 10. `avg_shortest_path_length`

含义：平均每个 episode 从起点依次访问各 subtask 目标的理论最短路径长度。

计算：

```text
episode.shortest_path_length = sum(subtask.shortest_path_length)
avg_shortest_path_length = mean(episode.shortest_path_length)
```

每段最短路径：

```text
shortest_distance(current_pose, subtask.target_position)
```

其中：

- 若 Habitat navmesh 可用，优先使用 geodesic distance。
- 若允许 Euclidean fallback 或 Habitat 失败，则退化为欧氏距离。
- 当前正式测试建议使用 `--no-euclidean-fallback`，避免不可达目标被低估。

解读：

- `avg_path_length / avg_shortest_path_length` 可粗略反映路径冗余。
- 若最短路径异常小或为 `0`，需检查 navmesh、layout object 加载和目标位置。

### 11. `dynamic_memory_accuracy`

含义：动态记忆命中准确率，表示在动态布局长期测试中，有多少 subtask 被当前长期记忆与闭环搜索成功解决。

在 `run_temporal_habitat_loop` 中，每个 episode 的记忆统计为：

```text
dynamic_memory_correct = found_count
dynamic_memory_total = len(episode.subtasks)
```

总体计算：

```text
dynamic_memory_accuracy =
    sum(dynamic_memory_correct) / sum(dynamic_memory_total)
```

解读：

- 它是 subtask 级的记忆成功比例，不是 episode 级成功率。
- 例如 `dynamic_memory_accuracy = 0.027` 表示大约 2.7% 的子任务被成功完成或记忆流程命中。
- 它可能大于 `success_rate`，因为 episode 只要有一个 subtask 失败就算整个 episode 失败。

### 12. `fixed_memory_accuracy`

含义：固定记忆基线准确率。

当前 `run_temporal_habitat_loop` 中该字段暂时写为：

```text
fixed_memory_correct = 0
fixed_memory_total = 0
```

总体计算：

```text
fixed_memory_accuracy =
    sum(fixed_memory_correct) / sum(fixed_memory_total)
```

当分母为 `0` 时，代码返回 `0.0`。

解读：

- 当前它不是有效实验结论，只是预留字段。
- 后续加入固定布局记忆基线后，才能用它比较动态记忆是否真正带来提升。

## 三、子任务与任务类型指标

这些指标来自 `by_task_type.json`，按 `task_type` 聚合。

当前主要任务类型包括：

- `open_vocab`：开放词汇目标搜索。
- `image_goal`：图像目标搜索。
- `language_goal`：语言描述目标搜索。
- `all`：所有子任务的总体聚合。

### 1. `subtasks`

含义：该任务类型下参与统计的子任务数量。

计算：

```text
subtasks = len(subtask_results_of_this_type)
```

### 2. 子任务级 `success_rate`

含义：该任务类型下，单个 subtask 最终到达目标范围内的比例。

计算：

```text
success_rate = successful_subtasks / subtasks
```

其中：

```text
subtask_success = distance_to_goal <= success_radius
```

解读：

- 它比 episode 级 `success_rate` 更细。
- 如果 episode 级 SR 为 0，但子任务级 SR 大于 0，说明系统能解决部分目标，但连续多目标任务链条仍不稳定。

### 3. 子任务级 `spl`

含义：单个 subtask 的成功加权路径效率。

计算：

```text
subtask_SPL =
    0, if subtask failed
    shortest_path_length / max(path_length, shortest_path_length), otherwise
```

然后对同一任务类型取平均。

### 4. `avg_distance_to_goal`

含义：该任务类型下，最终位姿到目标位置的平均距离。

计算：

```text
avg_distance_to_goal = mean(distance_to_goal)
```

其中：

```text
distance_to_goal = euclidean_distance(final_pose, subtask.target_position)
```

解读：

- 它能反映“虽然没有成功，但离目标是否更近”。
- 当 `success_rate = 0` 时，该指标比 SPL 更有诊断价值。

### 5. 子任务级 `avg_steps`

含义：该任务类型下平均每个 subtask 消耗的步数。

计算：

```text
avg_steps = mean(subtask.steps)
```

解读：

- 高步数 + 高距离通常表示搜索方向错误。
- 高步数 + 低距离可能表示接近目标但确认或导航终止机制有问题。

## 四、长期能力曲线指标

这些指标来自 `exploration_curve.json` 和 `temporal_summary.json`。它们用于回答核心问题：agent 在同一家庭环境中见过更多历史 layout 后，是否表现更好？

### 1. `seen_layout_count_before`

含义：当前 episode 开始前，agent 在同一 scene 下已经见过的历史 layout 数量。

解读：

- `0` 表示第一次进入该家庭状态，没有历史布局经验。
- 数值越大，表示 agent 应该拥有更丰富的 scene-level memory。

### 2. `sr_delta`

来源：`exploration_curve.json`

含义：相对于第一个历史经验分组的 episode 成功率变化。

计算：

```text
sr_delta = current_success_rate - baseline_success_rate
```

其中 baseline 是最小 `seen_layout_count_before` 分组。

### 3. `spl_delta`

来源：`exploration_curve.json`

含义：相对于第一个历史经验分组的 SPL 变化。

计算：

```text
spl_delta = current_spl - baseline_spl
```

### 4. `sr_gain_pct`

来源：`exploration_curve.json`

含义：相对于 baseline 的成功率百分比提升。

计算：

```text
sr_gain_pct =
    (current_success_rate - baseline_success_rate)
    / max(baseline_success_rate, 1e-6)
    * 100
```

注意：当 baseline 为 0 时，代码使用 `1e-6` 防止除零，因此该百分比可能非常大，不宜单独作为论文结论。

### 5. `spl_gain_pct`

来源：`exploration_curve.json`

含义：相对于 baseline 的 SPL 百分比提升。

计算：

```text
spl_gain_pct =
    (current_spl - baseline_spl)
    / max(baseline_spl, 1e-6)
    * 100
```

解读方式同 `sr_gain_pct`。

## 五、记忆检索与候选质量指标

这些指标主要来自 `memory_diagnostics.jsonl` 和 `temporal_summary.json`。

### 1. `found`

含义：该 subtask 是否在 benchmark 意义上成功。

计算：

```text
found = final_dist <= success_radius
```

其中：

```text
final_dist = euclidean_distance(final_pose, target_position)
```

解读：

- `found` 是子任务级最终成功标签。
- 它比 `perception_found` 更严格，因为它要求最终位姿确实靠近 benchmark 标注目标。

### 2. `found_rate`

含义：某一组 subtask 的最终成功比例。

计算：

```text
found_rate = count(found == true) / number_of_subtasks
```

它在 `temporal_summary.json` 中会按以下维度出现：

- `overall`
- `by_state_index`
- `by_seen_layout_count_before`

### 3. `perception_found`

含义：感知闭环是否认为目标已被观测确认。

根据参数不同，确认模式有两种：

- `semantic`：主要依赖检测标签或语义匹配。
- `spatial`：检测结果还需要在空间上接近 benchmark 目标，通常更适合正式评测。

当前推荐：

```bash
--target-confirmation-mode spatial
--target-confirmation-margin 1.0
```

解读：

- `perception_found = true` 不一定等于 benchmark 成功。
- 如果 `perception_found` 很高但 `found` 很低，可能存在误检测、语义别名错误、空间定位偏差或成功半径设置不匹配。

### 4. `sss`

含义：Subtask Search Steps，当前 subtask 消耗的搜索步数。

在 `run_temporal_habitat_loop` 中，它来自：

```text
sss = trace.steps
```

解读：

- 该值反映一个 subtask 的实际执行预算消耗。
- 它不是纯检索次数，而是闭环搜索过程中的执行步数。

### 5. `avg_sss`

含义：平均每个 subtask 的搜索步数。

计算：

```text
avg_sss = mean(sss)
```

解读：

- `avg_sss` 高但 `found_rate` 低，说明系统花了很多步仍未找到目标。
- 随着历史 layout 增加，如果长期记忆有效，理想上 `avg_sss` 应下降或至少不显著上升。

### 6. `mra`

含义：Memory Retrieval Accuracy，当前实现中可理解为 top-1 记忆候选是否命中目标。

计算：

```text
mra = (候选列表非空) and
      (第 1 个候选到目标的距离 <= success_radius)
```

代码逻辑：

```text
mra = bool(dists and dists[0] <= success_radius)
```

其中 `dists` 是候选点到 benchmark 目标位置的距离列表，顺序与候选排序一致。

解读：

- `mra` 衡量检索排序的第一名是否足够准确。
- 如果 `mra` 高但 `found_rate` 低，说明候选正确但导航执行或目标确认没有转化为成功。
- 如果 `mra` 低但 `ghr5` 高，说明候选池里有正确答案，但排序需要改进。

### 7. `ghr3`

含义：Goal Hit Rate at 3，top-3 候选中是否至少有一个落在目标成功半径内。

计算：

```text
ghr3 = any(distance(candidate_i, target) <= success_radius
           for candidate_i in top_3_candidates)
```

解读：

- 它衡量候选生成的召回能力。
- `ghr3 > mra` 时，说明排序或融合评分仍有改进空间。

### 8. `ghr5`

含义：Goal Hit Rate at 5，top-5 候选中是否至少有一个落在目标成功半径内。

计算：

```text
ghr5 = any(distance(candidate_i, target) <= success_radius
           for candidate_i in top_5_candidates)
```

解读：

- 它比 `mra` 和 `ghr3` 更宽松，更适合衡量记忆候选池是否包含正确区域。
- 如果 `ghr5 = 0`，说明检索候选整体离真实目标较远。
- 如果 `ghr5 > 0` 但 `found_rate = 0`，说明候选出现过正确区域，但闭环导航或终止机制未能把它转化为成功。

### 9. `min_dist`

含义：当前 subtask 的候选列表中，距离真实目标最近的候选距离。

计算：

```text
min_dist = min(distance(candidate_i, target_position))
```

若没有候选，则为 `null`。

解读：

- 它衡量候选池与真实目标的最近接近程度。
- 该指标下降通常表示长期记忆或检索质量在变好。

### 10. `avg_min_dist`

含义：一组 subtask 中 `min_dist` 的平均值。

计算：

```text
avg_min_dist = mean(min_dist for records with valid candidate)
```

解读：

- 越小越好。
- 当 `found_rate` 仍为 0 时，`avg_min_dist` 可以作为“是否正在接近正确区域”的早期信号。

### 11. `final_dist`

含义：subtask 结束时，agent 最终位置到 benchmark 目标位置的距离。

计算：

```text
final_dist = euclidean_distance(final_pose, target_position)
```

解读：

- `final_dist <= success_radius` 时，该 subtask 成功。
- 若 `min_dist` 很小但 `final_dist` 很大，说明候选曾经接近目标，但 agent 没有移动到该候选或路径执行失败。

### 12. `fallback_count`

含义：该 subtask 中由于没有有效候选或候选不可用而触发 fallback 的次数。

解读：

- 较高的 `fallback_count` 表示 Agentic-RAG 候选链路经常失效，被迫进入随机或探索策略。
- 若 fallback 高且 `candidate_recall_rate` 低，应优先检查 CLIP 阈值、目标名称映射和远程感知结果。

### 13. `memory_track_count`

含义：当前 scene-level memory 中维护的 object track 数量。

解读：

- 太低可能表示感知或记忆更新没有工作。
- 太高可能表示重复目标没有合并，导致记忆污染。

### 14. `peaks`

含义：当前 subtask 最后一次使用的候选列表，通常包含候选位置、标签、相似度、融合分数和来源。

解读：

- 用于检查 top-k 候选是否合理。
- 可与可视化页面中的候选点对应查看。

## 六、候选生成与融合指标

这些指标来自 `candidate_traces.jsonl`，也会被 `diagnose_temporal_run.py` 汇总。

### 1. `candidate_rounds`

含义：候选生成轮数。

计算：

```text
candidate_rounds = len(candidate_traces)
```

### 2. `rounds_with_candidates`

含义：产生了非空候选列表的轮数。

计算：

```text
rounds_with_candidates =
    count(len(top_candidates) > 0)
```

### 3. `rounds_without_candidates`

含义：没有产生候选的轮数。

计算：

```text
rounds_without_candidates =
    candidate_rounds - rounds_with_candidates
```

### 4. `candidate_recall_rate`

含义：候选生成召回率，即有候选的轮数比例。

计算：

```text
candidate_recall_rate =
    rounds_with_candidates / candidate_rounds
```

解读：

- 它不判断候选是否正确，只判断有没有候选。
- 如果该值很低，优先检查感知是否产生 object、CLIP embedding 是否为空、阈值是否过高、目标名称映射是否缺失。

### 5. `avg_candidates_per_round`

含义：每轮平均候选数量。

计算：

```text
avg_candidates_per_round =
    mean(len(top_candidates))
```

解读：

- 过低：召回不足。
- 过高：候选过散，排序和融合压力变大。

### 6. `avg_selected_score`

含义：每轮被选中候选的平均最终融合分数。

计算：

```text
avg_selected_score =
    mean(selected_candidate.S_final)
```

如果没有 `S_final`，诊断脚本会尝试读取候选的普通 `score`。

解读：

- 高分不一定代表正确，需要结合 `min_dist` 和 `ghr@k`。
- 如果高分候选总是远离目标，说明融合评分或先验存在偏差。

### 7. `selected_backend`

含义：被选中候选的来源统计。

常见来源可能包括：

- label / alias 精确匹配。
- remote CLIP text-image 相似度。
- Agent room / receptacle prior。
- fallback 探索候选。

解读：

- 如果长期主要来自 fallback，说明 RAG / CLIP 检索链路没有真正发挥作用。
- 如果主要来自 label，但 image_goal / language_goal 表现差，说明多模态检索没有充分启动。

### 8. `selected_labels`

含义：被选中候选的标签分布。

解读：

- 用于检查目标名称映射是否合理。
- 如果目标是 `chess`，但候选长期集中在无关标签，说明 alias 或 CLIP 文本查询需要调整。

### 9. `fallback_reasons`

含义：进入 fallback 的原因统计。

解读：

- 该字段可直接定位失败链路。
- 典型原因包括无候选、候选不可达、分数低于阈值等。

## 七、感知指标

这些指标来自 `observation_traces.jsonl` 和 `perception_summary.json`。

### 1. `detections`

含义：所有观测中记录到的检测结果总数。

诊断脚本计算：

```text
detections = len(observation_traces)
```

解读：

- 若为 `0`，说明远程感知链路未产生有效结果。
- 需要检查远程服务、SSH tunnel、GroundingDINO / MobileSAM、CLIP embedding 接口。

### 2. `positioned_detections`

含义：带有空间位置的检测数量。

计算：

```text
positioned_detections =
    count(record.pos_2d is not None or record.pos_3d is not None)
```

解读：

- 检测有标签但没有位置，无法形成有效导航候选。
- 低值通常与深度图、mask、相机参数或投影逻辑有关。

### 3. `clip_embedding_dims`

含义：观测中 CLIP embedding 维度的统计。

解读：

- 正常情况下同一实验应只有一种维度。
- 如果同时出现 512 和 768，说明混用了不同 CLIP 模型，检索相似度不可靠。

### 4. `top_labels`

含义：观测中出现频率最高的标签。

解读：

- 用于检查 GroundingDINO prompt 是否覆盖目标。
- 若目标标签从未出现，可能需要放宽目标名称映射或依赖 CLIP 文本检索。

### 5. `perception_summary`

含义：远程感知服务调用的工程统计。

常用于检查：

- 调用次数。
- 失败次数。
- 平均耗时。
- 远程服务是否稳定。

解读：

- 如果失败率高，先修远程服务稳定性，再分析算法。
- 如果耗时过高，可能需要降低 `--n-views`、图像分辨率或批处理感知请求。

## 八、记忆更新与负反馈指标

这些指标来自 `memory_updates.jsonl`、`negative_feedback.jsonl` 和 `scene_memory/*/scene_memory_final.json`。

### 1. `memory_events`

含义：记忆系统产生的更新事件总数。

计算：

```text
memory_events = len(memory_updates)
```

解读：

- 若为 `0`，说明感知结果没有进入长期记忆。
- 这通常是严重问题，会导致后续长期能力无法体现。

### 2. `by_event`

含义：按记忆事件类型统计。

常见事件：

- `new`：新增 object track。
- `merged`：将观测合并到已有 track。
- `migrated`：动态物体位置迁移或更新。
- `negative_feedback`：旧候选搜索失败后降低其可信度。

解读：

- `new` 多但 `merged` 少：可能存在重复建图或物体关联不足。
- `negative_feedback` 多但成功率低：可能一直在惩罚错误候选，但没有找到新候选。

### 3. `negative_feedback`

含义：当 agent 选择某候选并搜索失败时，对该候选或物体 track 增加负反馈。

用途：

- 降低旧位置的 `exist_prob`。
- 增加 `negative_feedback_count`。
- 避免 agent 在动态物体已移动后反复回到旧位置。

解读：

- 负反馈是长期动态环境中的关键机制。
- 若负反馈生效，后续同类目标候选不应持续集中在失败旧位置。

### 4. `scene_memory_final.json`

含义：某个 scene 的最终长期记忆状态。

重点字段通常包括：

- object identity。
- label / aliases。
- CLIP embedding。
- `pos_2d` / `pos_3d`。
- `last_update_time`。
- `stability`。
- `exist_prob`。
- `cooccur_stats`。
- `negative_feedback_count`。

解读：

- 这是判断“同一家庭长期能力”是否形成的核心产物。
- 不能只看最终 SR，还应检查 memory 中物体位置是否随 layout 状态合理迁移。

## 九、布局与时间序列指标

### 1. `layout_transitions`

来源：`layout_transitions.jsonl`

含义：记录同一 scene 中 layout 的进入和退出。

事件类型：

- `layout_enter`：进入某个动态布局。
- `layout_exit`：退出某个动态布局，并写入 memory snapshot。

解读：

- 它用于确认实验确实跨越多个 layout，而不是只在单一 HM3D 原始场景内运行。
- 长期能力实验必须检查该文件，确认多个 `state_index` 或多个 `layout_id` 被执行。

### 2. `state_index`

含义：动态家庭环境的时间状态编号。

解读：

- 相同 scene 下，不同 `state_index` 表示同一家庭在不同时间的物体状态。
- 正式长期评测应观察指标随 `state_index` 和 `seen_layout_count_before` 的变化。

### 3. `by_state_index`

来源：`temporal_summary.json`

含义：按时间状态聚合的检索与成功指标。

用途：

- 检查某些时间状态是否特别困难。
- 定位动态 layout 中目标迁移、遮挡或感知失败问题。

### 4. `by_seen_layout_count_before`

来源：`temporal_summary.json`

含义：按历史 layout 数量聚合的长期能力指标。

这是本文项目最关键的长期能力曲线之一。

理想现象：

```text
seen_layout_count_before 增加
=> found_rate / mra / ghr3 / ghr5 上升
=> avg_min_dist / avg_sss 下降
```

如果没有出现该趋势，说明长期记忆尚未有效改善搜索。

## 十、诊断报告指标

运行：

```bash
python -m RAANav.AgenticRAG.benchmark_adapter.diagnose_temporal_run \
  --output-dir <eval_output_dir> \
  --write-json <eval_output_dir>/temporal_run_diagnosis.json
```

会生成诊断聚合结果。

### 1. `perception_to_benchmark_found_gap`

含义：感知认为找到目标的次数，与 benchmark 实际成功次数之间的差距。

计算：

```text
perception_to_benchmark_found_gap =
    perception_found_count - benchmark_found_count
```

解读：

- 大于 0 且很大：感知确认可能过宽，或检测目标与 benchmark 标注目标不一致。
- 接近 0：感知确认与 benchmark 成功较一致。

### 2. `ghr5_to_found_gap`

含义：top-5 候选命中目标但最终没有成功的次数差。

计算：

```text
ghr5_to_found_gap = ghr5_count - found_count
```

解读：

- 大于 0：候选池里出现过正确区域，但导航执行、路径可达性或成功确认失败。
- 等于 0 且 `ghr5` 也低：主要问题在候选生成或长期记忆检索。

### 3. `avg_final_dist`

含义：平均最终位置到目标的距离。

计算：

```text
avg_final_dist = mean(final_dist)
```

越低越好。

### 4. `best_final_dist`

含义：所有 subtask 中最终位置最接近目标的一次距离。

计算：

```text
best_final_dist = min(final_dist)
```

用于判断系统是否偶尔接近目标。

### 5. `avg_candidate_min_dist`

含义：平均每个 subtask 的最近候选距离。

计算：

```text
avg_candidate_min_dist = mean(min_dist)
```

如果该值明显低于 `avg_final_dist`，说明候选比最终位置更接近目标，问题可能在导航执行。

### 6. `best_candidate_min_dist`

含义：所有 subtask 中最接近目标的候选距离。

计算：

```text
best_candidate_min_dist = min(min_dist)
```

### 7. `avg_final_minus_candidate_min_dist`

含义：最终位置平均距离与候选最近距离之间的差。

计算：

```text
avg_final_minus_candidate_min_dist =
    avg_final_dist - avg_candidate_min_dist
```

解读：

- 大于 0 且很大：候选比最终位置更好，执行或目标选择有问题。
- 接近 0：最终位置基本反映候选质量。

### 8. `failure_flags`

含义：自动诊断出的失败信号列表。

常见取值：

| flag | 含义 |
| --- | --- |
| `perception_empty` | 感知没有产生任何检测。 |
| `memory_not_updated` | 长期记忆没有更新事件。 |
| `retrieval_no_candidates` | 候选生成轮次存在，但没有产生候选。 |
| `candidates_far_from_goal` | top-5 候选没有命中过目标区域。 |
| `candidate_near_but_not_converted_to_success` | 候选接近目标，但最终没成功。 |
| `perception_goal_mismatch_or_false_positive_confirmation` | 感知确认与 benchmark 成功严重不一致。 |
| `negative_feedback_after_failed_candidates` | 失败后产生负反馈，说明系统在修正旧候选。 |
| `late_memory_improvement_signal` | 后期历史记忆分组出现改善信号。 |
| `healthy` | 成功率大于 0 且没有明显失败信号。 |

### 9. `failure_bucket`

含义：诊断脚本根据优先级给出的主要失败类型。

优先级大致为：

```text
perception_empty
memory_not_updated
retrieval_no_candidates
candidates_far_from_goal
perception_goal_mismatch_or_false_positive_confirmation
candidate_near_but_navigation_or_success_radius_failed
negative_feedback_after_failed_candidates
unsuccessful_unknown
healthy
```

解读：

- 这是最适合快速定位下一步 debug 方向的字段。
- 它不是论文指标，而是工程诊断标签。

## 十一、当前示例结果如何解读

示例输出：

```json
{
  "episodes": 10,
  "success_rate": 0.0,
  "spl": 0.0,
  "avg_steps": 73.6,
  "avg_elapsed_seconds": 135.4636382,
  "avg_path_length": 99.03919779999998,
  "avg_shortest_path_length": 35.70531610250473,
  "dynamic_memory_accuracy": 0.02702702702702703,
  "fixed_memory_accuracy": 0.0,
  "evaluated_episodes": 10,
  "trajectory_count": 10,
  "missing_episode_count": 0
}
```

逐项解释：

- `episodes = 10`：本次评测了 10 个 episode。
- `trajectory_count = 10` 且 `missing_episode_count = 0`：轨迹和 episode 对齐正常，评测输入没有缺失。
- `success_rate = 0.0`：没有任何 episode 完成所有 subtask。
- `spl = 0.0`：由于 episode 级成功率为 0，SPL 必然为 0。
- `avg_steps = 73.6`：平均每个 episode 执行了约 73.6 步，说明搜索预算被大量使用。
- `avg_path_length = 99.04`，`avg_shortest_path_length = 35.71`：实际路径约为理论最短路径的 2.77 倍，且仍未成功，说明路径效率和目标选择都存在问题。
- `dynamic_memory_accuracy = 0.027`：约 2.7% 的 subtask 在动态记忆流程中成功或被记为正确；这说明系统不是完全没有命中，但远不足以完成 episode 级任务。
- `fixed_memory_accuracy = 0.0`：当前固定记忆基线未启用，不应作为有效对比结论。

该结果的核心判断：

```text
系统已经完成真实闭环运行，但长期记忆尚未稳定转化为 episode 级成功。
下一步应重点检查候选质量、候选到导航成功的转化、目标名称映射和感知确认一致性。
```

## 十二、指标之间的常见误读

### 1. `success_rate = 0` 不等于系统完全无效

因为 episode 级成功要求所有 subtask 都成功。若存在部分子任务成功，应看：

- `by_task_type.json`
- `memory_diagnostics.jsonl`
- `dynamic_memory_accuracy`
- `found_rate`
- `ghr3` / `ghr5`

### 2. `perception_found` 不等于 `found`

`perception_found` 是感知确认，`found` 是 benchmark 空间成功。正式评测以 `found` / `success_rate` 为准。

### 3. `ghr5` 高但 `success_rate` 低不是矛盾

这说明候选池包含正确区域，但 agent 没有成功到达或确认。此时应检查：

- 路径是否可达。
- 候选选择是否被错误分数覆盖。
- `target-confirmation-mode` 是否过严或过松。
- 负反馈是否过早惩罚了正确候选。

### 4. `avg_min_dist` 下降是积极信号，但不是最终成功

`avg_min_dist` 只说明候选更接近目标，不说明导航完成。论文主结果仍应以 SR / SPL / found_rate 为主。

### 5. `fixed_memory_accuracy = 0` 当前不是负面结论

当前代码中固定记忆基线还未正式填充，该值为预留字段。

## 十三、建议论文与实验报告采用的指标层次

正式报告建议分三层呈现：

第一层：最终任务完成能力。

- Episode SR。
- Episode SPL。
- Subtask found_rate。
- Subtask avg_distance_to_goal。

第二层：长期记忆是否带来提升。

- 按 `seen_layout_count_before` 的 SR / SPL 曲线。
- 按 `seen_layout_count_before` 的 found_rate / mra / ghr5 曲线。
- avg_min_dist 随历史 layout 数的变化。
- avg_sss 随历史 layout 数的变化。

第三层：失败机制诊断。

- candidate_recall_rate。
- mra、ghr3、ghr5。
- perception_to_benchmark_found_gap。
- ghr5_to_found_gap。
- memory_events / negative_feedback。
- failure_bucket。

## 十四、推荐检查顺序

当一次实验结果不理想时，建议按以下顺序排查：

1. 检查 `missing_episode_count` 是否为 0，确认评测输入有效。
2. 检查 `observation_traces.jsonl` 是否有检测和空间位置。
3. 检查 `clip_embedding_dims` 是否一致。
4. 检查 `candidate_recall_rate` 和 `rounds_with_candidates`，确认候选链路是否启动。
5. 检查 `mra`、`ghr3`、`ghr5`，判断候选是否接近真实目标。
6. 检查 `ghr5_to_found_gap`，判断问题在候选还是导航转化。
7. 检查 `perception_to_benchmark_found_gap`，判断感知确认是否误报。
8. 检查 `memory_updates.jsonl` 和 `negative_feedback.jsonl`，判断长期记忆是否在更新和修正。
9. 打开 `visual_debug/index.html`，观察轨迹、目标点、候选点和记忆事件的空间关系。

## 十五、与项目目标的关系

本项目的核心目标是检验 agent 在同一家庭环境下的长期能力。因此，单次成功或失败不应作为唯一结论。更重要的是观察：

- 同一 scene 中，随着 `seen_layout_count_before` 增加，目标检索和到达是否改善。
- 动态物体移动后，agent 是否能降低旧位置权重并迁移到新高概率区域。
- image_goal 和 language_goal 是否真正利用多模态记忆，而不是退化为标签匹配。
- 负反馈是否减少重复访问失败位置。
- 长期记忆是否提高候选召回、降低搜索步数、缩短最终目标距离。

若长期曲线中 `found_rate`、`mra`、`ghr5` 上升，同时 `avg_min_dist` 和 `avg_sss` 下降，即使早期 episode 级 SR 仍低，也说明系统已经出现了可进一步优化的长期记忆信号。
