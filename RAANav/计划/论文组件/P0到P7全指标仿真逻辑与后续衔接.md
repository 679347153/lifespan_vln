# P0→P7 全指标仿真：实现逻辑与后续衔接

> 最后更新: 2026-04-12

本文档记录从 P0 静态基线验证到 P7 端到端实验运行器的**完整实现逻辑链条**，以及这套离线仿真与后续 habitat-sim 在线导航实验的衔接方式。

---

## 总体思路

核心问题：验证系统在**物体位置随时间变化**的动态环境中，语义记忆是否能正确更新、查询、遗忘。

实现策略：**不依赖 habitat-sim 实时导航**，用程序化方式生成各 epoch 的观测数据 (`floors_now`)，送入已有的 `run_merge()` 管线，再用 GMM 概率场 + 轻量候选点模拟评估。

```
变更脚本 (YAML)
    ↓  描述各物体在各 epoch 的位置/状态
EpochSimulator
    ↓  生成 floors_now → 调用 run_merge → floors_history
GMMEvaluator
    ↓  CLIP 搜索 + GMM 评分 → 概率场 → Top-K 峰值
LightweightNavSim
    ↓  逐候选点访问模拟 SSS
Metrics
    ↓  MRA / GHR@K / D-SR / SSS / MRR
run_experiment
    ↓  多消融条件 × 多 epoch → 对比表格
```

## 各阶段详细逻辑

### P0b：静态基线验证

**文件**: `eval/test_static_pipeline.py`

**目的**: 在物体位置完全不变的前提下，验证 merge + GMM 管线本身是否正确。如果静态场景下指标就异常，后续一切无意义。

**逻辑**:
1. 加载 T0 地图作为 `floors_history` 和 `floors_now`（完全相同）
2. 将 `floors_now` 重复送入 `run_merge()` 共 5 轮。每轮推进时间戳，但**所有物体位置不变**
3. 每轮 merge 后对 3-5 个标签做 CLIP + GMM 查询，检查：
   - `exist_prob` 是否稳定 ≈ 1.0
   - Top-1 峰值距 GT 位置 < 1m
   - 物体总数不异常增长
4. 验收标准：MRA 100%，位置漂移 0m，exist_prob > 0.99

**发现的问题与修复**:
- `exist_prob` 初始不恢复：原因是 `floors_now` 从 `floors_history` 拷贝时继承了衰减后的值 → 修复：每次生成 `floors_now` 前将所有物体 `exist_prob` 重置为 1.0（模拟"刚看到"）
- CLIP 无法 `RuntimeCLIPIndex`：改用 `transformers` 的 text-to-text 余弦相似度
- `occupancy_meta.npz` 的 `origin` 是 2 元素数组 `[origin_x, origin_z]`，不是 dict

### P1：变更脚本解析

**文件**: `eval/change_script.py` + `eval/scenarios/00814_changes.yaml`

**目的**: 用 YAML 文件描述"哪些物体在哪些 epoch 的位置是什么"。

**数据结构**:
```
ChangeScript
├── scene_id: "00814-p53SfW6mjZe"
├── n_epochs: 5
├── epoch_days: [1, 3, 7, 14, 30]
└── changes: List[ObjectChange]
       ├── obj_id: "chair_1_R0" (NO 类型为 null)
       ├── label: "chair"
       ├── change_type: SO | LRO | HRO | DO | NO
       └── positions: {epoch → {room, pos_3d} | null}
```

**核心方法**:
- `is_present(epoch)` — 该物体在该 epoch 是否存在
- `has_moved(epoch, threshold)` — 相比上一 epoch 是否超过阈值移动
- `get_moved_obj_ids(epoch)` — 本 epoch 所有已移动的 obj_id 列表

**陷阱**: YAML 解析器将裸 `NO` 识别为布尔 `False` → 解析时用 `str().upper()` 转换

**场景 00814 的变更脚本设计**:
- 3 个 HRO (chair, cushion, stool) — 每 epoch 在 R0/R1 间交替
- 2 个 LRO (lamp, basket) — 各仅移动一次
- 2 个 DO (box, toy) — 分别在 epoch 2 和 epoch 3 消失
- 2 个 NO (speaker, bowl) — 分别在 epoch 2 和 epoch 3 新增

### P2：Epoch 模拟器

**文件**: `eval/epoch_simulator.py`

**目的**: 根据变更脚本，为每个 epoch 生成 `floors_now`（机器人本轮"看到的"物体列表），然后调 `run_merge()` 更新 `floors_history`。

**核心逻辑** (`generate_floors_now(epoch)`):
1. 深拷贝 T0 基础地图（所有 SO 物体原样保留）
2. 遍历变更脚本：
   - **HRO/LRO 已移动**: 从 `floors_now` 中**移除旧 obj_id** → merge 时老节点因"没被看到"而 `exist_prob` 衰减；以**新 obj_id** 在新位置添加新物体 → merge 时作为新节点加入
   - **DO 已消失**: 从 `floors_now` 中移除 → 老节点持续衰减
   - **NO 首次出现**: 以新 obj_id 添加到 `floors_now`
3. 全部物体 `exist_prob = 1.0`（模拟"本轮全部看到了"）
4. 推进时间戳

**关键设计**: 物体移动 ≠ 修改位置坐标。而是**旧 ID 消失 + 新 ID 出现**。这确保了 merge 逻辑（基于 obj_id 匹配）能正确区分"同一物体没动"和"出现了一个新的同类物体"。

**`run_all_epochs()` 流程**:
```
for epoch in 0..4:
    floors_now = generate_floors_now(epoch)
    floors_history = run_merge(floors_now, floors_history, cfg)
    gt_layout = build_gt_layout(epoch)   # 该 epoch 的 GT 物体布局
```

**Object 构造注意**: `Object.__init__()` 要求 `region` 参数（多边形顶点列表），为新物体构造 0.5m 正方形 region。

### P3：指标计算

**文件**: `eval/metrics.py`

所有函数均为**纯计算函数**，不依赖文件 I/O 或模型。

| 函数 | 维度 | 输入 | 输出 |
|------|------|------|------|
| `compute_mra(peak, gt, r_hit)` | 记忆质量 | Top-1 峰值坐标 + GT 坐标 | bool |
| `compute_mra_min_dist(peak, all_gt, r_hit)` | 记忆质量 | Top-1 + 所有同标签 GT | (bool, float) |
| `compute_ghr_at_k(peaks, all_gt, k, r_hit)` | 记忆质量 | Top-K 峰值列表 | bool |
| `compute_d_sr(moved_results)` | 动态适应 | [bool, ...] | float |
| `compute_as(mra_by_epoch, moved_epoch)` | 动态适应 | 逐 epoch MRA 列表 | int \| None |
| `compute_sss(candidate_visits)` | 动态适应 | 候选点数 | int |
| `compute_mrr(predictions)` | 长期学习 | [{change_type, mra, ...}] | {type: rate} |
| `compute_sr(results)` | 传统 | [bool, ...] | float |
| `compute_all_metrics(query_results, r_hit)` | 汇总 | 批量查询结果列表 | dict |

### P4：GMM 评估器

**文件**: `eval/gmm_evaluator.py`

**职责**: 封装"给一个标签 + floors → 返回概率场峰值"的完整流程，供 P5/P7 调用。

**查询流程** (`GMMEvaluator.query(label, floors)`):
```
1. CLIP text-to-text 搜索: 遍历 floors 中所有物体标签，
   与查询标签做 cos sim，返回 sim ≥ 0.90 的 obj_id 列表
2. GMM 评分: 对每个命中物体算 Calculate_obj_Score
   (基于 N, stability, cfd)
3. 概率场构建: 在占据栅格上，以每个物体位置为中心、
   GMM 分数为幅度放置高斯核 (σ_base=1.5m)
4. 峰值提取: NMS 提取 Top-5 峰值 (最小间距 10 cells)
```

**设计**: 模块级缓存 CLIP 模型，首次加载约 5s，后续查询 <0.1s/标签。

**独立使用**:
```python
evaluator = GMMEvaluator(grid_dir="...", clip_min_score=0.90)
result = evaluator.query("chair", floors)
# result["peaks"] → [{world_x, world_z, prob}, ...]
result = evaluator.evaluate_against_gt("chair", floors, gt_positions)
# result 额外包含 mra, ghr3, ghr5
```

### P5：轻量导航模拟

**文件**: `eval/nav_sim_lightweight.py`

**目的**: 不启动 habitat-sim，纯粹在概率场上模拟"机器人依次前往候选点"的过程，计算 SSS。

**搜索逻辑** (`LightweightNavSim.search(label, floors, gt_positions)`):
```
1. 构建概率场，提取 Top-max_candidates 个候选点 (默认 10)
2. for step in 0..max_candidates:
       访问第 step 个候选点 (px, pz)
       if dist(px, gt_any) < r_hit:
           → found=True, sss=step+1, break
       else (miss):
           if neg_field_enabled:
               在 (px, pz) 注入负向高斯核
               (σ_neg = σ_base × 2.0, α = 0.3)
               从修正后的概率场重新提取剩余候选
               → 后续候选被"推开"
3. 返回 {found, sss, visited_points, mra, ...}
```

**负向高斯场的作用**: miss 后在概率场上叠加负值高斯，使得已失败区域的概率被压低，下一个候选点自然转向未探索区域。这是对 `nav_core/nav_strategy.py` 中 `NegativeGaussianField` 的离线等价：

| 在线导航 (nav_strategy.py) | 离线模拟 (nav_sim_lightweight.py) |
|---|---|
| 机器人物理移动到候选点 | 概率场上标记为"已访问" |
| 摄像头看不到目标 → `check_and_inject()` | 距 GT > r_hit → `_inject_negative_kernel()` |
| 实时更新概率场 | 修正副本 + 重新提取峰值 |
| `frontier_exploration_step()` 评估候选 | 直接取修正后的 Top-1 |

### P6：消融配置

**文件**: `eval/ablation.py`

6 种消融条件，通过覆盖 config 参数实现：

| 名称 | 改了什么 | 验证什么 |
|------|---------|---------|
| **Full** | 默认 | 完整系统 |
| **w/o NegGMM** | `neg_field_enabled=False` | 负向高斯场的贡献 → SSS 应升高 |
| **w/o Decay** | `missing_decay=1.0` | exist_prob 衰减的贡献 → DO 物体不会被遗忘 |
| **w/o Stability** | 所有物体 `stability=0.5` | stability 先验的贡献 |
| **w/o Merge** | 每 epoch 用 `floors_now` 不做 merge | 历史合并的贡献 → 退化为单帧 |
| **SingleMap** | w/o Merge + w/o NegGMM | 最简基线 |

### P7：实验运行器

**文件**: `eval/run_experiment.py`

**`run_experiment()` 完整流程**:
```
1. 加载 ChangeScript + map.yaml → apply_ablation 覆盖
2. EpochSimulator.run_all_epochs()
   → floors_history 逐 epoch 演化 + gt_layouts
3. 构建 GMMEvaluator + LightweightNavSim
4. for epoch in 0..4:
       确定查询列表:
         - 变更脚本中的 HRO/LRO/DO/NO 物体
         - 补充 5 个 SO 物体（基线参考）
       for label in 查询列表:
           nav_sim.search(label, floors, gt) → SSS/found/mra
       compute_all_metrics(epoch_queries) → 本 epoch 指标
5. compute_all_metrics(全部 queries) → 全局汇总
6. compute_mrr() → 按 change_type 分组的记忆保持率
```

查询每 epoch 约 12 个标签（7 变更 + 5 SO），5 epoch = 60 queries。CLIP 模型首次加载约 5s，后续每 query < 0.5s，单场景单消融约 2.5min。

## 已验证结果 (场景 00814)

```
Full:        MRA=0.917  GHR@3=0.950  D-SR=1.000  SSS_mean=1.035  SR=0.950
w/o NegGMM:  MRA=0.917  GHR@3=0.933  D-SR=1.000  SSS_mean=1.088  SR=0.950

MRR (Full):
  SO=1.000  LRO=1.000  HRO=0.867  DO=0.400  NO=1.000  overall=0.917
```

观察：
- SSS_mean：Full (1.035) < w/o NegGMM (1.088) → 负向高斯场确实减少候选点试错
- GHR@3：Full (0.950) > w/o NegGMM (0.933) → 负向高斯场改善候选列表质量
- DO 的 MRR 仅 0.4：符合预期，消失物体的老位置记忆随衰减变得不可靠
- HRO 的 MRR 0.867：移动物体仍有较高的记忆准确率（多峰 GMM 能覆盖新旧位置）

### P8：多场景变更脚本

**目标**: 为 3-5 个 HM3D 场景各写一份 `{scene_id}_changes.yaml`。

**步骤**:
1. 对每个新场景跑 `deep_exploration.py` → T0 地图 JSON + 占据栅格
2. 用 `export_scene_info.py` 导出房间/可放置区域，选择 HRO/LRO/DO/NO 候选物体
3. 按 `00814_changes.yaml` 格式编写新 YAML
4. `run_experiment.py` 直接可用（只改路径参数）

**场景选择建议** (对齐论文难度梯度):

| 难度 | 场景 | 房间数 | 物体数 | 变化强度 |
|------|------|--------|--------|---------|
| Easy | 小户型单层 | 2-3 | ~30 | 仅 SO + 少量 HRO |
| Medium | 00814 (已有) | 2 | 275 | 全五类 |
| Hard | 多楼层大户型 | 8+ | 100+ | 高频 HRO + 楼层间迁移 |

### P9：在线导航实验 (可选增强)

若论文需要真实导航结果而非轻量模拟：

**方式**：用 `scripts/sim_nav_loop.py` 的 `run_gmm_query` 管线替代 `LightweightNavSim`。

**复用逻辑**:
```
P2 的 EpochSimulator
    → 生成 floors_now
    → run_merge → floors_history       (不变)
    → 写出到 JSON

sim_nav_loop.py
    → 加载 floors_history 的 JSON
    → 启动 habitat-sim 导航
    → 实际走到候选点, 用摄像头确认 target_seen
    → 记录实际 SSS / 实际路径
    → 结果回传 → metrics.py 计算

消融：ablation.py 的 config 覆盖同样适用于 sim_nav_loop
```

具体衔接点：
1. `EpochSimulator.run_all_epochs()` 的 `floors_history` 可 `Floor.to_json()` 序列化
2. `sim_nav_loop.py` 已接受外部 `map_json` 参数
3. `NegativeGaussianField` 在 `nav_core/nav_strategy.py` 中已实现在线版
4. SSS 只需计数 `frontier_exploration_step()` 的 GMM 模式循环次数

## 关键设计决策回顾

| 决策 | 理由 |
|------|------|
| 物体移动 = 旧 ID 消失 + 新 ID 出现 | 保证 merge 基于 obj_id 匹配的逻辑正确工作 |
| 每 epoch 全部 exist_prob 重置为 1.0 | 模拟"全覆盖探索"——机器人看到了所有物体 |
| 轻量 SSS 而非真实导航 | 去耦导航效率(双腿)与记忆质量(大脑)，聚焦论文论点 |
| 负向高斯用修正概率场副本 | 不影响后续 epoch 的概率场（各 epoch 独立） |
| 消融通过 config 覆盖而非代码分支 | 消融之间共享同一套代码路径，避免维护分叉 |
